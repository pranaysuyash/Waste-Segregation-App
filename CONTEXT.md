# Domain Glossary — ReLoop Waste Segregation App

> This document defines the canonical domain language for the ReLoop project.
> All code, docs, and conversations should use these terms consistently.
> Implementation details live in code and ADRs — not here.
>
> **Architectural Decisions**: See `docs/adr/` for ADR-001 (Clean Architecture), ADR-002 (Riverpod State Management), ADR-003 (Data Sync Strategy), ADR-004 (Society Policy Override), and ADR-005 (Classification Pipeline).

## Core Waste Concepts

### WasteClassification
The central domain object produced by the classification pipeline. Represents a single waste item that has been identified, categorized, and annotated with disposal guidance. Every classification carries a category, subcategory, confidence score, disposal instructions, and provenance metadata (which model produced it, which policy was applied, which society override was active).

**Boundary**: A WasteClassification is immutable after creation. It is the output of classification and the input to policy evaluation. It is not a "prediction" — it is a resolved classification with full audit trail.

### Category
The top-level waste type (e.g., "Hazardous Waste", "Wet Waste", "Dry Waste", "Non-Waste"). Categories map to municipal disposal streams and determine which policy rules apply. Categories are fixed by the taxonomy — they do not change per city or society.

### SubCategory
The second-level classification within a category (e.g., "Battery" within "Hazardous Waste", "Food Scraps" within "Wet Waste"). SubCategories determine specific disposal steps and bin assignments. SubCategories are also taxonomy-stable.

### DisposalInstructions
The actionable guidance for how to dispose of a classified item. Contains a primary method, step-by-step instructions, urgency flag, and optional recycling notes. Generated by the classification pipeline or the backend `generateDisposal` function. Not the same as policy rules — disposal instructions are item-specific, while policy rules are region-specific.

### Recycling Taxonomy
The hierarchical classification system that connects visual identification to material properties to disposal guidance. The taxonomy is the "join key" across systems — it maps resin codes (RIC #1–#7), material categories, waste types, and colloquial names to canonical disposal paths. Taxonomy is versioned and region-aware.

## Classification Pipeline

### Layer 0 — Deterministic
The first layer of classification. Pure client-side logic — no network, no model download. Includes barcode lookup (Open Food Facts API) and color histogram analysis (HSV-based clustering). Produces a `Layer0Result` with a `Layer0Decision` of `accept`, `hint`, or `escalate`.

**Boundary**: Layer 0 is always available and always free. It never fails — it either accepts or escalates. It does not produce a full WasteClassification — only a hint or a confident-enough result.

### Layer 1 — On-Device ML
The second layer. On-device machine learning model inference (TFLite). Not yet deployed in production — currently wired through `FakeLocalClassifier` which returns null and escalates to cloud.

### Layer 2 — Cloud Cheap
The third layer. Cloud-based classification using cost-effective models. Called via the `classifyImage` Firebase callable. The canonical production classification path in release mode.

### Layer 3 — Cloud Strong
The fourth layer. Reserved for high-confidence or complex classifications. Uses stronger, more capable models. Currently implicit in the API fallback chain — no dedicated route exists yet.

### AnalysisSource
The provenance tag indicating which model or method produced a classification. Stored as a string field on `WasteClassification` with static constants defined for the three canonical values:

- `cloud_primary` — Classification produced by the cloud API (default)
- `local_experimental` — Classification produced by on-device ML (Layer 1)
- `local_failed_fallback_cloud` — On-device ML failed, fell back to cloud

Inferred from `source`, `modelSource`, and `classificationLayer` fields when not explicitly set. Recorded on every WasteClassification for audit and cost tracking.

### ClassificationLayer
The layer at which a classification was resolved. Stored as a string field on `WasteClassification` with five canonical values:

- `layer0_deterministic` — Barcode lookup or color histogram (free, always available)
- `layer1_on_device` — On-device ML model inference (TFLite/CoreML)
- `layer2_cloud_cheap` — Cost-effective cloud model (production default)
- `layer3_cloud_strong` — High-capability cloud model (implicit fallback)
- `null` — Unknown or legacy classification (pre-pipeline records)

Runtime-only field (not persisted to Hive) — can be derived from `modelSource` and `modelVersion` for historical records.

### Confidence
A numeric score (0.0–1.0) indicating how certain the classification model is about its result. Raw confidence comes from the model; calibrated confidence applies category-level overrides. Confidence drives policy application: below 0.50, municipal policy is skipped entirely; below 0.70, safety overrides are demoted to warnings.

### Quality Gate
A pre-flight check that rejects images before any classification routing. Rejects blurry, dark, or undersized (<300px) images. Prevents wasting cloud API calls on poor-quality inputs.

## Policy Engine

### LocalPolicyEngine
The engine that evaluates municipal and society-level waste policy rules against a classified waste item. Takes a WasteClassification and region, resolves the appropriate city plugin, applies confidence gating, safety overrides, and society deltas, and produces a `LocalPolicyDecision`.

### LocalPolicyDecision
The output of policy evaluation. Contains: whether policy was applied, which plugin and rule pack were used, compliance status, violations, warnings, confidence gating state, provenance metadata, and society override details. Attached to the WasteClassification for persistence and display.

### ComplianceStatus
The result of policy evaluation for a specific item in a specific region. Values: `compliant` (rules satisfied), `requires_attention` (low-confidence warnings), `violation` (rules broken). Driven by confidence gating — the same item can be a violation at high confidence and a warning at low confidence.

### CityPlugin
A region-specific configuration that maps geographic regions to municipal policy rules. Each city plugin has a plugin ID (e.g., `bbmp_bangalore`, `bmc_mumbai`), rule packs, authority metadata, and source provenance. Plugins are registered in the `LocalGuidelinesManager` and resolved by region string.

### LocalPolicyRulePack
A collection of policy rules for a specific city plugin. Each rule pack has a version, a set of rules (with rule IDs like `bbmp_hazardous_special_disposal`), and metadata. Rule packs are static data — they do not change at runtime.

### SafetyOverride
A policy rule type that applies regardless of ML classification flags. Used for safety-critical items (e.g., hazardous waste always requires special disposal). Enforced at high confidence (≥0.70); demoted to warning at low confidence. The `safetyOverrideAlways` check type ensures deterministic safety enforcement.

### ConfidenceGating
The mechanism that adjusts policy enforcement based on classification confidence. At high confidence (≥0.70), all rules apply as violations. At medium confidence (0.50–0.70), violations are demoted to warnings. Below 0.50, municipal policy is skipped entirely with a fallback metadata warning.

## Society Policy Override Layer

### SocietyPolicyOverride
A delta layer registered by an apartment society (RWA) that overrides specific city-level policy rules. Contains: society ID, society name, base plugin ID (must match the city plugin), and a list of `RuleOverride` objects. Stored in Firestore under `society_policies/{societyId}`.

**Boundary**: A SocietyPolicyOverride is always scoped to a single city plugin. If the society's base plugin doesn't match the resolved city plugin, the override is not applied and a conflict is recorded.

### RuleOverride
A single rule change within a society's policy. Contains: category key (which waste category the override applies to), override type (what aspect is changed), new value, and optional description. RuleOverrides are additive — they add or change rules, they don't remove city-level rules.

### RuleOverrideType
The type of rule being overridden. Values: `binColor` (different bin assignment), `collectionFrequency` (different pickup schedule), `disposalMethod` (different disposal process), `collectionLocation` (different drop-off point), `bannedItem` (item prohibited by society), `customInstruction` (society-specific guidance).

### BasePluginId
The city plugin ID that a society override is anchored to. Must match the resolved city plugin for the override to apply. If there's a mismatch (e.g., society registered for BMC Mumbai but user is in BBMP Bangalore), the override is skipped and a conflict is recorded.

### SocietyConflict
A detected mismatch between a society override and the resolved city policy. Recorded when: (1) the society's base plugin doesn't match the city plugin, or (2) both city and society define rules for the same category. Conflicts are surfaced in `LocalPolicyDecision.societyConflicts` and displayed in the `PolicyProvenanceCard`.

### PolicyProvenanceCard
A UI component that surfaces governance metadata for a classification. Shows: city plugin name, authority, guidelines version, society name (if active), applied overrides, and detected conflicts. Provides transparency into which rules were applied and why.

## Offline & Queue

### OfflineDegradationTier
The level of service degradation when the device is offline. Values: `fullOffline` (Layer 0 + Layer 1), `deterministicOnly` (Layer 0 only), `queued` (image queued for cloud processing when connectivity returns).

### OfflineQueueService
A persistent local queue that stores classifications pending cloud processing. Supports retry with backoff. Permanent failures move to a dead-letter queue.

### DeadLetterClassification
A classification that failed all retry attempts in the offline queue. Stored with full error details for audit and manual retry. Users can retry, delete, or clear all dead-letter items via the Impact Dashboard.

## User & Gamification

### UserProfile
The persistent user identity and preferences. Contains: user ID, email, display name, gamification profile, consent status, region preferences. Stored in Firestore and Hive for offline access.

### GamificationProfile
The user's gamification state. Contains: points, streaks, achievements, challenges, and community contributions. Drives engagement through rewards for correct waste segregation behavior.

### TokenWallet
The user's virtual currency balance. Tokens are earned through correct classifications and can be spent on premium features. Supports backup/restore, cross-device sync (one-way push), and purchase via DodoPayments.

## Infrastructure

### Firebase Callable
A server-side function invoked by the Flutter client via Firebase SDK. Used for `classifyImage` (classification proxy) and `generateDisposal` (disposal instruction generation). Handles authentication, rate limiting, and App Check enforcement.

### App Check
Firebase's client attestation service. Conditional enforcement — the callable classification function can enforce App Check when configured, but the backend environment controls whether enforcement is required.

### Backend Proxy
The server-side classification path. In release mode, the Flutter client routes classification through `BackendProxyProvider` to the `classifyImage` Firebase callable. The callable calls OpenAI/Gemini and returns the result. Avoids exposing API keys in the client binary.

### Local Guidelines Plugin
A city-specific configuration object that provides: region mapping, rule packs, authority metadata, source provenance, and compliance logic. Plugins are registered in `LocalGuidelinesManager` and resolved by region string.

## Terminology Pitfalls

These terms are overloaded or ambiguous in the codebase. Use the canonical definitions above.

### `source` (overloaded)
The field `source` on WasteClassification means "which classification path produced this result" — values like `barcode:${barcodeResult.source}`, `color_histogram`, `layer1_on_device`, `cache`, `ai_reanalysis`, `ai_analysis_$provider`. This is DIFFERENT from `analysisSource` (provenance tag: `cloud_primary`, `local_experimental`, `local_failed_fallback_cloud`) and `modelSource` (which AI model). *Example: `source: 'barcode:12345'` is the Layer 0 result, while `analysisSource: 'cloud_primary'` is the overall provenance.* When discussing classification provenance, always specify which `source` field you mean.

### `validation` (overloaded)
Three distinct meanings: (1) schema validation (community feed data quality), (2) event validation (analytics consent check), (3) server-side validation (token spend authorization). When discussing validation, specify which type.

### `policy` (overloaded)
Two distinct meanings: (1) municipal policy rules (city-level waste regulations), (2) society policy overrides (apartment-level deltas). The engine that evaluates both is `LocalPolicyEngine`. When discussing policy, specify whether you mean city rules, society deltas, or both.

## First Principles

These are the long-term domain modeling principles for this project:

1. **Glossary-first**: Before writing code or docs, check CONTEXT.md for canonical terms. If a term isn't here, add it. *Consequence: inconsistent terminology creates confusion and bugs when the same word means different things to different developers.*
2. **Additivity over replacement**: Society overrides add/change rules, never remove city-level safety rules. This is enforced in code and must remain true. *Consequence: breaking additivity weakens city-level safety guarantees.*
3. **Confidence drives enforcement**: Policy application is gated by classification confidence. Below 0.50 → policy skipped entirely. 0.50–0.70 → violations demoted to warnings. Above 0.70 → full enforcement. This is the core safety mechanism. *Consequence: removing confidence gating would enforce rules on uncertain classifications, leading to false positives.*
4. **Provenance is non-negotiable**: Every classification must record which model, policy, and society override produced it. This is for governance, debugging, and cost tracking. *Consequence: missing provenance makes it impossible to debug misclassifications or track costs.*
5. **Layers progress by cost**: Free methods first (Layer 0: barcode/color histogram), then paid cloud (Layer 2: GPT-4.1-nano). Escalate only when lower layers produce `escalate` decision. *Consequence: skipping free layers wastes money; skipping paid layers sacrifices quality.*
6. **Conflicts are surfaced, not resolved**: When city and society rules conflict, the UI shows both. The user decides which applies. Automatic resolution would hide governance decisions. *Consequence: hiding conflicts lets incorrect rules be enforced silently.*

## Cross-Cutting Terms

### Provenance
The audit trail recording which model, policy, and society override produced a classification. Includes: `analysisSource`, `modelRoute`, `modelSelectionStrategy`, `policyPackId`, `societyId`, `societyName`. Stored on every WasteClassification for debugging, cost tracking, and governance.

### Confidence State
The policy-level interpretation of classification confidence. Values: `applied` (normal enforcement), `gated` (violations demoted to warnings), `not_applied` (policy skipped entirely below 0.50). Stored on `LocalPolicyDecision` for UI display.

### Region
A geographic identifier string (e.g., "Bangalore, IN", "Pune, IN") used to resolve city plugins and policy rules. Regions are mapped to plugin IDs via the `LocalGuidelinesManager`. The region can be set explicitly by the user or detected via GPS (planned).
